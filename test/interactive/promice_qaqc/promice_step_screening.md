# PROMICE surface step-shift screening (all staged sites)

Generated by screening every staged station with `buildPromiceData` (which
stages the de-stepping DETECTION channels `step_detected_flag`,
`step_correctable_flag`, `step_magnitude`) and tallying the per-site detection
record. The de-stepping CORRECTION is opt-in at analysis time via
`icemodel.forcing.destepSurface` (default: correct UNAMBIGUOUS steps only).

Detection runs on the site's cumulative surface series (`ablation` [+down] at
ablation sites, `surface_height` [+up] at accumulation sites) between adjacent
FINITE samples (a gap interior is interpolation, not a step). Evidence lines:

- **magnitude** (GATE): a jump faster than the plausible per-step rate bound
  (`max_rate` over the inter-sample interval). Only rate-implausible jumps are
  candidates.
- **implausible**: `|jump| > max_step` (1.0 m) across a single interval — no
  physical process produces it (sensor reset / re-survey / installation jump).
- **transition**: within `tol_days` of a known station handover (not available
  in the staged product: only a SITE-level install date is staged, so this line
  is currently inert; the FACT that a site merges multiple AWS is in the
  `multistation` column).
- **season**: a melt-signed jump in the accumulation/winter season that also
  clears `max_step` (ablation belongs to the melt season).

Classification: **UNAMBIGUOUS** = magnitude gate AND a corroborating line
(implausible / transition / season); these are correctable by the default
transform. **AMBIGUOUS** = the magnitude gate alone; FLAGGED, never
auto-corrected.

## Honest caveats

- **Only MIT carries clearly-correctable installation steps.** MIT's two ~5.9 m
  jumps at 2009-08-11/12 (single-hour, grossly implausible, ~11.9 m total) are
  the unambiguous case the user flagged; the default transform levels them.
- **Accumulation sites show very high DETECTED counts** (e.g. CP1 ~10k, SDL
  ~12k). These are the rate gate firing on the noisy, heavily gap-bridged
  `z_surf_combined` across many short observed segments. Nearly all are
  AMBIGUOUS and are NEVER corrected; the handful classified unambiguous are
  >1 m single-hour glitches/spikes (e.g. KAN_U has 6, mostly transient up/down
  spikes that level to a small net offset). The high ambiguous density is
  conservative flagging, not correction.
- **QAS_U's "step" is a gap-bridged change, not a discrete jump.** The apparent
  ~2 m offset at 2010-10-18 spans a 61-day gap (~0.03 m/day, plausible), so it
  is correctly NOT flagged as a step; the GAP flag covers it. QAS_U is a known
  station merge (QAS_Uv3/QAS_U), but without staged per-station handover dates
  the transition evidence line cannot confirm a step there — this is reported
  honestly rather than auto-corrected.
- **site_type here is the OPERATIONAL discriminator** (presence of `z_ice_surf`
  in the L3 file), which can disagree with the readme Table 1 "Site type" for
  marginal local glaciers whose L3 file ships no `z_ice_surf` (e.g. ZAC_A,
  WEG_B): they screen as accumulation because they carry only `z_surf_combined`.

## How to regenerate

```matlab
% per site, in-memory, no figure needed:
[~, meta] = icemodel.forcing.buildPromiceData(site, frequency="hourly");
meta.steps_detected      % total candidate steps
meta.steps_correctable   % unambiguous (correctable) count
meta.step_record         % per-step {time, magnitude, evidence, classification}

% apply the opt-in correction at analysis time (default: unambiguous only):
[corrected, record, flags] = icemodel.forcing.destepSurface( ...
   Data.Time, Data.ablation, mode="unambiguous");
```
